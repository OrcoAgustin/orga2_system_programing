limit: 
    Specifies the size of the segment. The processor puts together the two segment limit fields to form 
    a 20-bit value. The processor interprets the segment limit in one of two ways, depending on the 
    setting of the G (granularity) flag:
    • If the granularity flag is clear, the segment size can range from 1 byte to 1 MByte, in byte incre
    ments.
    • If the granularity flag is set, the segment size can range from 4 KBytes to 4 GBytes, in 4-KByte 
    increments.
    The processor uses the segment limit in two different ways, depending on whether the segment is 
    an expand-up or an expand-down segment. See Section 3.4.5.1, “Code- and Data-Segment 
    Descriptor Types,” for more information about segment types. For expand-up segments, the offset 
    in a logical address can range from 0 to the segment limit. Offsets greater than the segment limit 
    generate general-protection exceptions (#GP, for all segments other than SS) or stack-fault excep
    tions (#SS for the SS segment). For expand-down segments, the segment limit has the reverse 
    function; the offset can range from the segment limit plus 1 to FFFFFFFFH or FFFFH, depending on 
    the setting of the B flag. Offsets less than or equal to the segment limit generate general-protection 
    exceptions or stack-fault exceptions. Decreasing the value in the segment limit field for an expand
    down segment allocates new memory at the bottom of the segment's address space, rather than at 
    the top. IA-32 architecture stacks always grow downwards, making this mechanism convenient for 
    expandable stacks.

Base:
    Defines the location of byte 0 of the segment within the 4-GByte linear address space. The 
    processor puts together the three base address fields to form a single 32-bit value. Segment base 
    addresses should be aligned to 16-byte boundaries. Although 16-byte alignment is not required, 
    this alignment allows programs to maximize performance by aligning code and data on 16-byte 
    boundaries.

G:
    Determines the scaling of the segment limit field. When the granularity flag is clear, the segment 
    limit is interpreted in byte units; when flag is set, the segment limit is interpreted in 4-KByte units. 
    (This flag does not affect the granularity of the base address; it is always byte granular.) When the 
    granularity flag is set, the twelve least significant bits of an offset are not tested when checking the 
    offset against the segment limit. For example, when the granularity flag is set, a limit of 0 results in 
    valid offsets from 0 to 4095.

P:
    Indicates whether the segment is present in memory (set) or not present (clear). If this flag is clear, 
    the processor generates a segment-not-present exception (#NP) when a segment selector that 
    points to the segment descriptor is loaded into a segment register. Memory management software 
    can use this flag to control which segments are actually loaded into physical memory at a given 
    time. It offers a control in addition to paging for managing virtual memory.
    Figure 3-9 shows the format of a segment descriptor when the segment-present flag is clear. When 
    this flag is clear, the operating system or executive is free to use the locations marked “Available” to 
    store its own data, such as information regarding the whereabouts of the missing segment.

DPL:
    Specifies the privilege level of the segment. The privilege level can range from 0 to 3, with 0 being 
    the most privileged level. The DPL is used to control access to the segment. See Section 5.5, “Priv
    ilege Levels,” for a description of the relationship of the DPL to the CPL of the executing code 
    segment and the RPL of a segment selector.

S:
    Specifies whether the segment descriptor is for a system segment (S flag is clear) or a code or data 
    segment (S flag is set).

2.1
pic Inicialización del PIC (pic_reset)

El PIC es el controlador que recibe las interrupciones de hardware (reloj, teclado, etc.) y se las pasa a la CPU con un número de interrupción. Hay dos en cascada: el PIC1 (maestro) atiende las IRQ 0 a 7 y el PIC2 (esclavo) las IRQ 8 a 15, conectado a la IRQ2 del PIC1.

Por defecto el PIC1 mapea sus IRQ en las interrupciones 8 a 15, que colisionan con las excepciones de la CPU (por ejemplo, el 8 es Double Fault y el 13 es #GP). Por eso hay que remapearlo: el PIC1 pasa a usar las interrupciones 32 a 39 (0x20 a 0x27) y el PIC2 las 40 a 47 (0x28 a 0x2F). Así el reloj (IRQ0) queda en la interrupción 32 y el teclado (IRQ1) en la 33.

Para esto se le envían a cada PIC cuatro palabras de configuración (ICW), en orden y sin escrituras intermedias:

ICW1 (puerto de comando, 0x11): inicia la inicialización, modo cascada, e indica que se enviará ICW4.
ICW2 (puerto de datos, 0x20 / 0x28): offset base de las interrupciones, que es el remapeo.
ICW3 (puerto de datos, 0x04 en PIC1 / 0x02 en PIC2): configuración de la cascada. El PIC1 recibe una máscara que indica que su esclavo está en la IRQ2, y el PIC2 recibe el número de IRQ del maestro al que está conectado.
ICW4 (puerto de datos, 0x01): modo 8086.

Al final se escribe la máscara de interrupciones (0xFF), que deja todas las IRQ deshabilitadas hasta que se llame a pic_enable.

manejo de memoria 
Ya viendo la memoria física en forma más general, vemos que se divide
en: *kernel*, *área libre kernel* y *área libre tareas*.

El área asociada al *kernel* corresponde al primer MB de memoria, el
*área libre kernel* a los siguientes 3 MB, y el *área libre tareas*
comienza en el cuarto MB de memoria.

La administración de las áreas libres de memoria (área libre de kernel y
área libre de tareas) se realizará a partir de una región de memoria
específica para cada una. Podemos comprenderlas como un arreglo
predefinido de páginas y dos contadores de páginas, uno para kernel y
otro para usuarix, que indican cuál será la próxima página a emplear de
cada región. Para páginas de kernel el arreglo va de `0x100000` a
`0x3FFFFF` y para páginas de usuarix de `0x400000` a `0x2FFFFFF`. Luego
de cada pedido incrementamos el contador correspondiente. En el
contexto de la materia no implementaremos un mecanismo que permita liberar
las páginas pedidas. Vamos a referirnos al módulo que implementa este
mecanismo como la **unidad de manejo de memoria**, o en inglés, *memory
management unit*, MMU.


paginacion
1. El problema que resuelve la paginación

Cada tarea quiere creer que tiene toda la memoria para ella, con direcciones que arrancan en 0. Pero la RAM real es una sola y se comparte. Entonces hay dos mundos:

Direcciones virtuales: las que ve el código de la tarea.
Direcciones físicas: las posiciones reales en la RAM.

La MMU traduce de virtual a física, y para eso se usa la paginación.

2. Qué es una página

Cortás la memoria en bloques de 4 KB. Un bloque de memoria virtual es una página, y un bloque de RAM real es un marco (o página física). Traducir es decir “esta página virtual vive en este marco físico”.

3. Lo que te estaba confundiendo: una tabla de páginas NO es una página con direcciones adentro de forma suelta

La tabla de páginas es una estructura que ocupa una página de RAM (4 KB), porque justo entran 1024 entradas de 4 bytes. Cada entrada (PTE) dice: “la página virtual número tanto está en este marco físico”, más unos flags (presente, R/W, U/S).

O sea, hay dos tipos de páginas de RAM:

Páginas que contienen datos o código de la tarea.
Páginas que contienen estructuras de paginación (directorio y tablas).

Las dos ocupan memoria física y las dos hay que pedirlas.

4. Cómo se conecta todo con el CR3

Es una cadena de punteros, todos a direcciones físicas:

CR3 → directorio → tabla de páginas → página de la tarea

CR3 guarda la dirección física del directorio.
Cada entrada del directorio apunta a una tabla de páginas.
Cada entrada de la tabla apunta a una página de datos/código.

5. Cómo se traduce una dirección (ejemplo)

Una dirección virtual de 32 bits se parte en tres:

[10 bits: índice en directorio | 10 bits: índice en tabla | 12 bits: offset]

Tomá la dirección 0x00001234:

Índice de directorio = 0
Índice de tabla = 1
Offset = 0x234

La MMU hace: va al directorio (CR3), mira la entrada 0 y obtiene la dirección de una tabla. Va a esa tabla, mira la entrada 1 y obtiene el marco físico. Le suma el offset 0x234 y ya tiene la dirección física real.

2, admin y user 
    Las estructuras de paginación (PDE y PTE) tienen un solo bit para esto, el U/S (User/Supervisor):

U/S = 0: supervisor. Solo accede código con CPL 0, 1 o 2.
U/S = 1: usuario. Acceden todos los niveles, incluido el CPL 3.

La CPU agrupa los 4 anillos en dos categorías: los niveles 0, 1 y 2 cuentan como “supervisor” y el 3 como “usuario”.

Los 4 niveles (0 a 3) los tenés en la segmentación: el DPL de los descriptores de la GDT y de la IDT, y el CPL/RPL de los selectores. Es fácil confundirlos porque en el TP vos usás solo el 0 y el 3.

Si la consigna pide explicar cómo se combina con los permisos, el chequeo se hace en los dos niveles de la tabla (PDE y PTE) y gana el más restrictivo. Para que una tarea de usuario acceda a una página, el bit U/S tiene que estar en 1 en ambas entradas. Lo mismo pasa con R/W para escritura.

1,b)

    La dirección lógica es un selector más un offset. El selector te manda a un descriptor de la GDT, que dice dónde arranca el segmento (la base). La CPU suma base + offset y obtiene la dirección lineal
    La memoria física se corta en bloques de 4 KB (las páginas). La idea es que la dirección lineal no apunta directo a la memoria física, sino que hay que consultar una “agenda” para saber en qué bloque físico está cada página. Esa agenda tiene dos niveles, como un libro con índice de capítulos y, adentro de cada capítulo, un índice de páginas.

    Para eso la CPU parte la dirección lineal de 32 bits en tres pedazos:

    Los 10 bits de arriba dicen “qué capítulo”, o sea qué entrada del directorio.
    Los 10 bits del medio dicen “qué página dentro del capítulo”, o sea qué entrada de la tabla de páginas.
    Los 12 bits de abajo dicen “qué línea dentro de la página”, o sea la posición dentro del bloque de 4 KB.
    Cambiar CR3 cambia toda la agenda de golpe. Por eso cada tarea puede tener su propio CR3 y creer que tiene toda la memoria para ella, aunque físicamente sus páginas estén desparramadas y mezcladas con las de otras. Y como el índice es de dos niveles, no hace falta tener armada una tabla gigante: solo creás las tablas de las zonas que realmente usás.

1,c)
    D (Dirty): la CPU lo pone en 1 la primera vez que se escribe en la página. Le sirve al SO para saber que la página se modificó y que, si la desaloja, tiene que guardarla antes. Solo tiene efecto en la PTE. Lo limpia el SO, nunca la CPU.
    A (Accessed): la CPU lo pone en 1 la primera vez que se lee o escribe la página. El SO lo usa para saber qué páginas se usaron hace poco (por ejemplo, para elegir cuál desalojar). Lo limpia el SO.
    PCD (Page Cache Disable): con 1, la página no se cachea y cada acceso va directo a memoria. Se usa para memoria mapeada a dispositivos, donde un valor cacheado sería un valor viejo.
    PWT (Page Write-Through): define la política de escritura del caché para esa página. Con 1, las escrituras se propagan a memoria al mismo tiempo que se escriben en el caché (write-through). Con 0, la escritura queda en el caché y baja a memoria después (write-back).
    U/S (User/Supervisor): con 0, solo accede código de supervisor (CPL 0, 1 o 2). Con 1, también accede el nivel de usuario (CPL 3). Un acceso de usuario a una página con U/S = 0 genera #PF.
    R/W (Read/Write): con 0, la página es de solo lectura. Con 1, se puede leer y escribir. Escribir en una página de solo lectura genera #PF. Para CPL 3 se respeta siempre; para CPL 0 depende del bit WP de CR0.
    P (Present): con 1, la página está en memoria y la traducción sigue. Con 0, la CPU no traduce y salta #PF. El resto de los bits de la entrada quedan libres para el SO.

1,d)
    Para que una página sea accesible desde user (CPL 3) tiene que tener U/S=1 en ambos niveles. Para que sea escribible desde user, R/W=1 en ambos. Alcanza con que uno de los dos diga “no” para que el acceso falle con #PF.

Hay un detalle con R/W: lo anterior vale para accesos de usuario. Para accesos en modo supervisor (CPL 0, 1 o 2), si CR0.WP = 0, el kernel puede escribir en páginas read-only igual. Si CR0.WP = 1, también se respeta el R/W en modo supervisor. La tabla del manual (Vol. 3, Combined Page-Directory and Page-Table Protection) lo marca con esa distinción.

1,e)
    5 páginas: 1 de directorio + 1 de tabla + 3 de memoria (2 de código y 1 de pila). 

1,g)
    La TLB (Translation Lookaside Buffer) es una caché chica y rapidísima, dentro de la MMU, que guarda las traducciones dirección virtual → dirección física usadas recientemente.
    Sin TLB, cada acceso a memoria con paginación de dos niveles costaría 3 accesos: uno al directorio, uno a la tabla de páginas y recién después el acceso real al dato. Con la TLB, si la traducción está (hit), se resuelve en un ciclo o dos sin tocar la memoria. Solo si no está (miss) se hace el page walk completo y se carga la entrada en la TLB.

    ¿Por qué hay que purgarla (tlbflush)?

    Porque la TLB es una copia de lo que hay en el directorio y las tablas de páginas, y el hardware no la mantiene coherente automáticamente con esas estructuras en memoria. Si el kernel modifica un PDE o PTE (cambia el marco físico, saca el bit de presente, cambia permisos, etc.), la TLB puede seguir teniendo la traducción vieja y la CPU la va a seguir usando:

    Accedés a una página que ya desmapeaste → la TLB todavía la traduce.
    Cambiás los permisos a solo lectura → la TLB sigue permitiendo escritura.
    Remapeás una página a otro marco → seguís escribiendo en el marco anterior.

    Por eso, después de tocar las estructuras hay que invalidar:

    invlpg <dir>: invalida la entrada de una dirección virtual puntual.
    Recargar CR3 (mov cr3, ...): purga (casi) toda la TLB. Es lo que pasa también en un cambio de espacio de direcciones (cambio de proceso), porque las traducciones de un proceso no valen para el otro. (Las entradas globales, bit G, pueden sobrevivir al recargar CR3, típicamente las del kernel.)
    ¿Qué atributos tiene cada entrada de la TLB?

    Cada entrada guarda básicamente:

    La página virtual (el tag, usado para matchear).
    El marco físico (la dirección base física de la página).
    Los atributos de la PTE/PDE: bit de presente, R/W (lectura/escritura), U/S (usuario/supervisor), bits de accessed (A) y dirty (D), y otros como PWT/PCD (política de caché) y G (global).

    Una entrada de la TLB es, en esencia, una copia de la entrada de la tabla de páginas más el tag de la dirección virtual. (En arquitecturas modernas se suman identificadores de espacio de direcciones, como PCID, pero eso no es necesario para el TP.)

    Al desalojar una entrada de la TLB, ¿se afecta la tabla original?

    Depende del bit dirty (y del accessed).

    En general, desalojar una entrada no modifica la tabla original: simplemente se descarta la copia, porque la tabla de páginas es la fuente de verdad.
    La excepción son los bits A y D: esos los actualiza el hardware. El bit accessed se setea en la PTE cuando se usa la traducción, y el bit dirty se setea en la PTE cuando se hace una escritura a la página. Si la TLB mantiene esos bits en la entrada cacheada, la información de modificación tiene que terminar reflejada en la PTE. En el caso de x86, el procesador escribe el bit D (y A) en la PTE en memoria en el momento en que se produce el acceso/la escritura que lo requiere, así que al desalojar la entrada no queda nada pendiente por “bajar” en la práctica. Conceptualmente, la respuesta esperada es: sí, en el caso de los bits A/D, la información tiene que reflejarse en la entrada original de la tabla; en todo lo demás el desalojo simplemente descarta la copia sin afectar la 
    tabla.

    1. Estructuras nuevas que necesitás

    Una entrada en la GDT por cada tarea, de tipo TSS descriptor. Cada tarea tiene su TSS (Task State Segment), y la GDT necesita un descriptor que apunte a cada una.
    Una TSS por tarea (2 TSS). Ahí se guarda el contexto de la tarea cuando no está corriendo: registros generales, EIP, EFLAGS, selectores de segmento, CR3, y la pila de nivel 0 (ESP0/SS0).
    Un directorio de páginas propio por tarea (2 page directories). Es lo que hace que cada tarea vea su propia memoria. Su dirección física va en el CR3 guardado en la TSS.
    Sus page tables correspondientes (las que hagan falta para mapear código, datos y pila de cada tarea).
    Una TSS extra para la tarea inicial, y otra para la tarea idle si el esquema lo pide, porque el procesador necesita un lugar donde guardar el contexto de “quien venía corriendo” cuando hacés el primer salto a una tarea. Ojo: depende de cómo lo plantee tu cátedra, fijate en el enunciado si piden tarea inicial/idle.

    2. Entradas nuevas en estructuras ya definidas

    GDT: las entradas de TSS mencionadas arriba (2 para las tareas, más 1 o 2 si están la inicial y la idle). Además, si no los tenías, los segmentos de código y datos de nivel 3 para las tareas de usuario.
    IDT: una entrada para la interrupción del reloj (el timer), que es la que dispara el scheduler, y una para la syscall si las tareas la usan. Si ya las tenías definidas, no se agrega nada nuevo.

    3. Registros a configurar

    TR (Task Register): hay que cargarlo con el selector de la TSS de la tarea inicial (ltr). Sin eso no se puede hacer el primer cambio de tarea.
    CR3: cambia con cada tarea (se carga desde la TSS al saltar), apuntando al directorio de páginas de la tarea que entra.
    Los registros de la PIC/PIT para que el reloj interrumpa periódicamente (si el scheduler es por tiempo).

    4. Formato y dónde están almacenadas

    GDT: tabla en memoria (la dirección y el tamaño están en el registro GDTR). Cada entrada es un descriptor de 8 bytes. Para una TSS: base (dirección de la TSS), límite (0x67 como mínimo, 104 bytes), tipo 1001 (TSS disponible), bit S = 0, DPL, bit P.
    TSS: estructura de 104 bytes en memoria (la base está guardada en su descriptor de la GDT). Tiene los campos que te nombré arriba.
    Page directory / page tables: en memoria física, páginas de 4 KB con entradas de 4 bytes (dirección base + bits de present, read/write, user/supervisor). El CR3 apunta al directorio.
    TR: registro del procesador que guarda el selector (índice en la GDT) de la TSS actual.


2.
    Qué es y cuándo se produce

    Cambio de contexto es sacar de ejecución una tarea guardando su estado, y poner a correr otra restaurando el suyo. En nuestro sistema se produce cuando interrumpe el reloj y el scheduler decide pasar a la siguiente tarea. También puede pasar cuando una tarea termina o se desaloja.

    Efecto sobre los registros

    Cambia todo el estado arquitectural de la tarea:

    Registros generales (EAX, EBX, ..., ESP, EBP).
    EIP y EFLAGS.
    Selectores de segmento.
    CR3, o sea el espacio de direcciones. Esto es clave: no es solo guardar registros, también cambia la paginación.

    Dónde se guarda el estado

    Con pushear a la pila vas bien. La pila es una opción válida: cada tarea tiene la suya, y guardar el contexto ahí funciona muy bien (es lo que hace un kernel típico). La otra opción es guardarlo en una estructura en memoria.

    Qué mecanismo da el procesador

    El procesador ofrece el cambio de tarea por hardware, basado en la TSS. Si hacés un jmp far (o call, o una interrupción por task gate) a un selector de TSS, el procesador guarda solo el estado de la tarea actual en su TSS, carga el estado de la nueva desde la otra TSS, y actualiza TR.

    Qué vamos a usar en su lugar

    Por lo que plantea la pregunta (“en su lugar”), usamos un cambio de contexto por software: lo hacemos nosotros en código del kernel. La idea es guardar los registros de la tarea saliente (en su pila o en una estructura), cambiar CR3 y ESP a los de la tarea entrante, y restaurar sus registros. Del mecanismo por hardware solo seguimos usando la TSS para una cosa: guardar ESP0/SS0, la pila de nivel 0 a la que el procesador salta cuando una tarea de usuario es interrumpida.

3.
    ¿Por qué cargar TR si no usamos el cambio por hardware?

    Porque el procesador lo sigue consultando por otro motivo: cuando una tarea de nivel 3 es interrumpida (reloj, syscall, excepción), el procesador pasa a nivel 0 y necesita una pila de nivel 0. Esa pila la saca de la TSS apuntada por TR: carga SS0:ESP0 y ahí empieza a pushear (SS, ESP, EFLAGS, CS, EIP de la tarea interrumpida).

    Si TR no está cargado con un selector válido, la primera interrupción que venga desde nivel 3 explota (falla y, como la falla también necesita pila, termina en triple fault). Por eso:

    Cargamos TR una sola vez con ltr, apuntando al descriptor de TSS en la GDT.
    Esa TSS es una sola, y de ella usamos casi exclusivamente SS0/ESP0.
    En cada cambio de contexto hay que actualizar ESP0 en esa TSS para que apunte a la pila de nivel 0 de la tarea que entra. Si no, la próxima interrupción pisaría la pila de otra tarea.

    ¿Qué pasa si no hay tareas para ejecutar o están todas suspendidas?

    El scheduler no puede quedarse sin nada a qué saltar. La solución es una tarea idle:

    Siempre está disponible: el scheduler la elige cuando no hay ninguna tarea viva/ejecutable. Nunca se suspende ni se desaloja.
    Tiene su propio contexto (pila, y su directorio de páginas o el del kernel). Normalmente corre en nivel 0.
    Su código es un loop que no hace nada útil, típicamente hlt dentro de un jmp/loop, para no quemar CPU.
    Las interrupciones tienen que estar habilitadas (sti) cuando corre. Si hacés hlt con IF=0, el procesador queda colgado para siempre, porque nada lo despierta. Con IF=1, el próximo tick del reloj lo despierta, el scheduler revisa si alguna tarea volvió a estar ejecutable y, si no, vuelve a idle.

4.
    ¿Qué hace el scheduler?

    Es el componente del SO que decide qué tarea corre en el procesador y por cuánto tiempo. Con una sola CPU (o menos CPUs que tareas) las tareas compiten por ella, y el scheduler arbitra esa competencia:

    Elige, entre las tareas listas para ejecutar, cuál es la siguiente.
    Dispara el cambio de contexto cuando corresponde (en nuestro TP, en cada tick del reloj).
    Sabe cuándo no hay nadie para correr y manda a la idle.
    Lleva el control del estado de cada tarea (corriendo, lista, suspendida/bloqueada, terminada).

    Así se logra la ilusión de que varias tareas corren “a la vez” y se reparte el uso de la CPU.

    ¿A qué nos referimos con que usa una política?

    Hay que separar mecanismo de política:

    Mecanismo: el cómo. Guardar el contexto, cambiar CR3, actualizar ESP0, saltar a la otra tarea. Eso es siempre lo mismo.
    Política: el criterio para decidir a quién le toca y cuánto corre. Es la regla de decisión del scheduler.

    Ejemplos de políticas:

    Round Robin: se recorren las tareas en orden circular, cada una con el mismo quantum (es la más simple y la que suele usarse en el TP).
    Por prioridades: corre la de mayor prioridad que esté lista.
    FIFO / FCFS: se ejecutan en orden de llegada hasta que terminan.
    SJF: primero la de menor tiempo estima

5.
    La idea: multiplexación en el tiempo (time-sharing)

    La CPU ejecuta una sola tarea por vez, pero el SO la va alternando entre las tareas tan rápido que, a escala humana, parece que corren todas a la vez.

    Cómo se logra

    Interrupción del reloj (timer): un temporizador (el PIT) interrumpe a la CPU periódicamente, cada pocos milisegundos. Cada tarea corre durante un quantum de tiempo.
    El scheduler toma el control: al llegar la interrupción, el procesador pasa a nivel 0 y salta al handler del reloj, que llama al scheduler. Ahí la tarea no tiene forma de negarse: es desalojo (preemption), el SO le quita la CPU sin que la tarea coopere.
    Cambio de contexto: se guarda el estado de la tarea saliente (registros, EIP, EFLAGS, etc.), se carga el de la entrante, incluyendo su CR3, y se retoma justo donde esa tarea había quedado.
    Repetir: cada tarea avanza un poquito en cada turno.

    Por qué parece simultáneo

    Cada tarea guarda y recupera su estado completo, así que “no se entera” de que fue pausada: para ella la ejecución es continua. Y como los quantums son cortos y los cambios son rápidos, desde afuera se ve progreso en todas al mismo tiempo. Pero paralelismo real (ejecución literalmente simultánea) solo existiría con varias CPUs o núcleos; acá es concurrencia.

    Para la respuesta del TP, con esto alcanza: time-sharing + interrupción del reloj + scheduler + cambio de contexto = ilusión de simultaneidad.
